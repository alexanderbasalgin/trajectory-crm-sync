# Ночная синхронизация amoCRM → Postgres: решение тестового задания

Условие задания: [TASK.md](TASK.md). Первый коммит репозитория - исходный код без изменений, поэтому все правки видны в diff.

## Итог в цифрах

Замеры на фейковой CRM (api_value ≈ 1.5 КБ на сущность), PostgreSQL 17, VPS на 2 vCPU. Скрипты: [`bench.py`](bench.py),
для исходного кода - тот же генератор поверх кода из первого коммита.

| | Было (исходный код) | Стало |
|---|---|---|
| 1 000 покупателей + 2 500 сделок | 247 с, 20 995 SQL-команд | **1.6 с, 16 команд** |
| 20 000 покупателей + 50 000 сделок | оценка ≈ 6-7 ч, ≈ 420 тыс. команд | **48 с, 247 команд** (повторный прогон: 58 с, 189) |
| Пик памяти Python на 20k/50k | оценка ≈ 200-300 МБ: итоговое чтение всей таблицы в ORM | **≈ 90 МБ** (RSS процесса ≈ 320 МБ с интерпретатором и библиотеками) |

Исходный код растёт как ~N^1.5: при удвоении объёма с 500/1 250 до 1 000/2 500 время выросло с 86 до 247 с.
Оценка для 20k/50k - экстраполяция этой зависимости.

## Что было дорого

1. **Поиск без индекса.** Каждый покупатель и сделка ищутся через `amo_customers @> ...` / `amo_leads @> ...`
   по JSONB без индекса - это полный скан таблицы. На прогоне 70 тыс. сущностей × 2-3 поиска × десятки тысяч строк:
   квадратичная сложность, она и даёт часы.
2. **Запрос и commit на каждую сущность.** ~6 команд на сущность (поиск по id, поиск по логину, UPDATE `jsonb_set`, COMMIT),
   ≈ 420 тыс. команд и столько же сетевых round-trip.
3. **Повторное чтение всей таблицы в конце** (`select(AbstractCustomer).all()`): все записи с полным JSON в памяти ORM,
   а затем commit на каждой итерации фильтра каждой сущности.

## Что изменено

**Схема:** добавлены GIN-индексы `jsonb_path_ops` на `amo_customers` и `amo_leads` ([`models.py`](models.py),
миграция [`migrations/001_jsonb_gin_indexes.sql`](migrations/001_jsonb_gin_indexes.sql) с `CONCURRENTLY`).
Они обслуживают любой containment-поиск `@>`: по id и логину в ночном прогоне, по точному логину и названию в остальных
частях системы. Связь сделка-покупатель по-прежнему задаётся общей записью `abstract_customer`, формат JSON в полях не менялся.

**Прогон** ([`sync.py`](sync.py), точка входа `collect_leads_customers(is_full=True)` в [`main.py`](main.py)):

1. **Индекс в памяти.** Один потоковый запрос читает из Postgres только `(id, логин)` вложенных покупателей и сделок,
   без `api_value`. Все поиски из бизнес-правил дальше - O(1) по словарям. На 70 тыс. сущностей это ≈ 20-30 МБ.
2. **Сбор.** Сущности из CRM обрабатываются по одной в исходном порядке, поэтому семантика последовательных
   поисков и слияний сохраняется (например, сделка видит покупателей, обработанных раньше в этом же прогоне).
   Решения принимаются по индексу, а JSON сущностей пачками по 1 000 уходит во временную таблицу одной командой
   `INSERT ... SELECT FROM jsonb_to_recordset`. В памяти только индекс и текущая пачка.
3. **Применение.** Затронутые записи идут блоками по 500: один SELECT строк блока, один SELECT их сущностей из staging,
   слияния, upsert сущностей и чистка в Python, затем один `UPDATE ... FROM jsonb_to_recordset` и один `INSERT`
   на блок. Неизменившиеся записи не переписываются.
4. **Чистка** выполняется в том же проходе по затронутым записям; записи, которых не было в выгрузке, удаляются одной
   командой `DELETE ... WHERE NOT (id = ANY(...))`. Повторного чтения всей таблицы нет.
5. **Одна транзакция и один commit** на весь прогон: читатели не видят промежуточного состояния, а падение посередине
   не оставляет полуобработанных слияний.

Число команд на 20k/50k: 1 (индекс) + 70 (staging) + ~58 блоков × 3-4 команды + 2-3 (DDL и удаления) ≈ 250.
Потоковое чтение индекса добавляет ~6 FETCH серверного курсора.

## Найденные расхождения с правилами и падения (исправлено)

1. **Удаление переставало работать.** Новая запись получает `id` только после commit, а в `ids_map` попадает раньше,
   с ключом `None`. В любом прогоне, где появился хотя бы один новый покупатель, `DELETE ... WHERE id NOT IN (NULL, ...)`
   не удаляет ни одной строки, а записи, созданные в прогоне, падают с `KeyError` на этапе чистки
   (воспроизводится на исходном коде: `KeyError: 990`).
2. **После слияния сделка терялась.** `lead_action` после слияния делает `return` без записи самой сделки и возвращает
   `None`, дальше `abc_customer.id` падает с `AttributeError`, и сделка не попадает ни в запись, ни в `ids_map`.
3. **Слияние не переносило `ids_map`.** Покупатели и контакты удалённой записи считались «не из выгрузки»
   и вычищались из выжившей. Кроме того, при слиянии терялись `send_methods`.
4. **Фильтр чистки проверял не тот элемент.** В `filter_merge_abstract_customer` условие написано по `l`
   (элемент внешнего цикла), а не по `c`, поэтому список фильтровался неверно. Плюс commit на каждой итерации и падение
   на сущности без `name`.
5. **Контакты сделок не учитывались.** `amocrm.Lead` не разбирал `_embedded`, поэтому `lead.contacts` всегда был пуст,
   и контакты, связанные только со сделками, удалялись чисткой.
6. **Пустая выгрузка стирала таблицу.** CRM, ответившая 204 на первой странице, неотличима от «покупателей нет»,
   и полный проход удалял все записи. Теперь при пустой выгрузке чистка пропускается с ошибкой в логе.
7. **Ошибка одной сделки вела к удалению её данных.** Сделка с битыми полями не попадала в `ids_map`, и чистка
   удаляла её прежнюю версию. Теперь такая сущность защищена от чистки, ошибка логируется и считается в статистике.
8. **Прерванный сбор.** Если CRM упала посередине, собранное до этого момента сохраняется, а удаление
   не запускается (как и требуется), после чего исключение пробрасывается дальше.

## Что оставлено и почему

- **JSONB-формат записей `abstract_customer`.** Его читают другие части системы, условие разрешает его сохранить,
  а с GIN-индексами он выдерживает и ночной прогон, и поиск по логину/названию. Нормализация в таблицы
  `amo_customer` / `amo_lead` с B-tree по `crm_id`, `login`, `name` и внешним ключом на `abstract_customer` была бы
  чище, но требует переписать всех читателей; это следующий шаг, если JSON-поиск станет узким местом.
- **Правило неоднозначного логина для сделок.** В условии оно сформулировано для покупателей; для поиска сделки
  по логину покупателя сохранено то же поведение, что и в исходном коде: больше одной записи - совпадение не используется.
- **Пропуск статусов** `111349` (покупатели) и `143` (сделки) только в неполном проходе - как в исходном коде.
- **Хелперы в `abstract_customer.py`** (`get_abccustomer_by_*`, `create_or_update_*`) оставлены для остального кода;
  ночной прогон их больше не использует, `get_customer_json` / `get_lead_json` используются как раньше.
- **Клиент amoCRM** не трогался, кроме разбора `_embedded` у сделок: его в репозитории нет целиком (`get_schema`, `as_dict`).

## Тесты

16 тестов на живом PostgreSQL ([`tests/test_sync.py`](tests/test_sync.py)), CRM подменяется фейковыми сущностями:
каждое правило из условия, слияние с переносом сущностей и `send_methods`, чистка (не из выгрузки, «удалить» в имени,
пустая запись), прерванный сбор, неполный проход, пустая выгрузка, битая сущность, идемпотентность повторного прогона
и проверка, что число команд не растёт с числом сущностей (< 60 на 10 тыс.).

```bash
docker run -d --name crm-pg -e POSTGRES_PASSWORD=test -e POSTGRES_DB=crm -p 127.0.0.1:5432:5432 postgres:17
pip install -r requirements.txt
TEST_DATABASE_URL=postgresql+psycopg://postgres:test@localhost:5432/crm pytest -q tests
TEST_DATABASE_URL=postgresql+psycopg://postgres:test@localhost:5432/crm python bench.py --customers 20000 --leads 50000
```

В зависимости добавлены `psycopg[binary]` (драйвера PostgreSQL в исходных requirements не было), `requests`
(его импортирует `amocrm.py`) и `pytest`.
